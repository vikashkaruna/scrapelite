### Item 8 — six bugs, one of them much bigger than first reported

**Danger Zone — root cause found, not just a stale doc claim.** `netlify/functions/account-state.js` called `authenticateBearer(event.headers?.authorization || ...)` — a **bare string** — instead of `authenticateBearer(event, {label})`. The shared helper expects the full Netlify event object and reads `.headers` off it itself; handed a string, `event?.headers?.authorization` on a string is always `undefined`, so the helper always saw an empty header and 401'd **every** signed-in request, unconditionally. `fetchAccountState()` treats any non-OK response as `{available:false}` by design (never throws), and `DangerZone.jsx`'s only gate is `if (!state?.available) return null` — so the whole section silently vanished, with no console error anywhere. Confirmed with a before/after test run: 13 of 15 tests in `account-state.test.js` failed against the pre-fix code (the test file's own mock had been matching the BUG's wrong contract, `{userId}`, instead of the real `{ok,user,client}` shape — that's exactly why the suite stayed green while the endpoint was broken in production).

Also added the plan-aware deletion gating the user specified: migration `0033_deletion_period_end_gate.sql` extends `request_account_deletion` so an account on an active paid plan gets `deletion_purge_after = GREATEST(period_end, now()+grace_days)` instead of a flat 30-day grace — never purged before the period they paid for ends, but never loses the recovery window either if their plan happens to be expiring soon. **Scoping call, confirmed with the user via AskUserQuestion mid-session:** v1.0 has no real recurring/auto-renewing billing (one-time Razorpay Orders only — `docs/RECURRING-BILLING-DEFERRAL.md`), so the "guide user to deactivate recurring subscription" step from the request doesn't exist yet and was explicitly scoped out — revisit when v2.0 ships real recurring billing.

**billing-purge.js's `PURGE_TABLES`** — 12 of the 13 discoverability tables + `referral_codes` + `workspace_members` (14 total) added, all confirmed to carry a plain `user_id` column matching the existing `user_id=eq.<id>` delete mechanism. Four tables from the same migrations do NOT fit that mechanism and are documented in a new exported `RETAIN_TABLES` map with per-table reasons: `referral_redemptions` (no `user_id` column, and it's the REFERRER's evidence too, not only the purged user's), `audit_events` (nullable `user_id` with `ON DELETE SET NULL` — an audit-trail table, same posture as `ops_audit_log`), `workspaces` (owned via `owner_id`, shared with other members — purging one member must never delete a workspace others still use), `workspace_invites` (owned via `invited_by`, expires on its own clock). New `netlify/__tests__/audit/purge-table-parity.test.js` scans the three migrations and asserts every table they introduced is in exactly one of `PURGE_TABLES`/`RETAIN_TABLES`.

**reengagement.js** — confirmed the documented defect: it selected a `user_email` column `scheduled_tasks` never had (only `user_id`). Rewrote `fetchActiveUsers()` to select `user_id` and resolve the real email via the Supabase Auth Admin API (same call `admin-users.js` already makes). New `netlify/__tests__/reengagement-handler.test.js` drives the real exported `handler` end-to-end (the old test file only ever covered pure helpers, never the HTTP path — which is exactly why the defect shipped unnoticed).

**usage_records/usage_alerts RLS** — `usageRepo.js` used to call the Supabase JS client directly from the browser with the anon key for every visitor (guest or signed-in), which the `anon full access` policy made world-readable/writable. New `netlify/functions/usage-sync.js` (service key) is now the only write/read path; `usageRepo.js` calls it via `fetch`. Migration `0034_usage_rls.sql` drops the anon policy — no anon or authenticated access remains on either table (they're keyed on `session_id`, not `user_id`, for guests, so there's no per-row RLS check to write; it's straight to service-key-only, matching the 0029-0031 pattern).

**"Sync public link"** — confirmed the documented defect. New `netlify/functions/public-reports.js` moves the write off the browser's direct Supabase upsert entirely; ownership on re-publish is checked server-side against a client-supplied `sessionId` in the POST **body** (never a header — the RLS policy's header-based branch was unusable because nothing ever sent it, and deliberately stays unused: `public read` exposes every column including `session_id`, so header-based ownership would let any reader of a published link take it over). `shareService.js`'s write path now posts to this function; the old client-side "probe after RLS denial" logic is gone since the server reports `refreshed:false` directly instead of throwing.

**complianceEngine.test.js hitting real DNS** — confirmed and fixed the same way the LinkedIn suite already was: added `vi.mock("../../functions/lib/publicUrl.js", ...)` so `fetchPublicUrl`'s SSRF-guard DNS resolution never runs. Suite dropped to <500ms from what used to be real-DNS-timeout-dependent.

**Visual regression suite** — regenerated all 11 baselines (spot-checked two diffs visually first via the Read tool's image support — confirmed legitimate accumulated feature growth, e.g. the pricing matrix, Go plan, and my own Research Pack addition, not breakage) and wired `test:e2e:visual` into `test:all` (deliberately **not** `test:prepush`, matching the existing smoke/full split). Two real, previously-undiagnosed sources of cross-run flakiness found and fixed in `home.spec.js`/`pricing.spec.js`:
  - A `document.fonts.ready` wait added after `networkidle` — these two specs deliberately allow real Google Fonts (`externalFonts:"allow"`), and font-swap reflow could still be in flight when `networkidle` fires.
  - `page.emulateMedia({reducedMotion:"reduce"})` in `beforeEach`, **plus** an explicit wait for `.try-demo-cta-final` (Home's `TryExampleDemo.jsx` auto-play completion marker) before screenshotting. The real root cause: even under `prefers-reduced-motion` (which zeroes the demo's internal delays to 0ms), the component's chained `setInterval`/`setTimeout` step machine still takes several real event-loop ticks to settle — and `networkidle` doesn't track JS timers at all, only network requests. A screenshot could land mid-step, and since each step reveals more content the page's full height genuinely differed run to run (observed: 2433 / 2629 / 2693px swings on the exact same URL). Confirmed stable across 5 repeated runs solo and 3 repeated full-suite runs (33/33) after the fix.
