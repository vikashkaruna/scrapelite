# 03 — Design (Phase 2 SDLC output)

> Generated by the `sdlc-datiq-quality-gate` prompt.
> The design picks a shape that satisfies the Phase-1 requirements **without inventing complexity**. Where I had to make a trade-off, I list the rejected alternative.

## 1. Architecture overview

The test gate is a **layered pyramid** that mirrors the FR taxonomy in `02-requirements.md`. Each layer has a single job, a single tooling choice, and a single CI hook. New R-numbered features drop in at the appropriate layer without re-architecting.

```
                        ┌───────────────────────────────┐
                        │      Visual regression        │  Playwright `toHaveScreenshot`
                        │      (FR-V, 8 specs)          │  8 stable pages, 32 snapshots
                        ├───────────────────────────────┤
                        │      Accessibility            │  vitest-axe + @axe-core/playwright
                        │      (FR-A, 7 specs)          │  Component + page + keyboard
                        ├───────────────────────────────┤
                        │      Security                 │  Beyond the secret-pattern script
                        │      (FR-X, 4 files)          │  XSS, auth bypass, coupon tamper
                        ├───────────────────────────────┤
                        │      E2E (Playwright journeys)│  Multi-step user flows
                        │      (FR-J, 10 specs)         │  with mocked /api/* boundary
                        ├───────────────────────────────┤
                        │      Smoke (Playwright)       │  Port of legacy 89 checks
                        │      (FR-K, 23 specs)         │  < 60 s, runs on every PR
                        ├───────────────────────────────┤
                        │      System (provider tree)   │  Vitest + jsdom + MemoryRouter
                        │      (FR-S, 6 specs)          │  Cross-cutting behaviour
                        ├───────────────────────────────┤
                        │      Functional (page-level)  │  Vitest + jsdom + MemoryRouter
                        │      (FR-F, 18 specs)         │  Route renders + happy path
                        ├───────────────────────────────┤
                        │      Integration (components) │  Vitest + jsdom + @testing-library
                        │      (FR-I, 25 specs)         │  Component + context interactions
                        ├───────────────────────────────┤
                        │      Contract (server)        │  Vitest + Node + vi.mock(fetch)
                        │      (FR-C, 21 specs)         │  Every /api/* + lib helper
                        ├───────────────────────────────┤
                        │      Unit (pure logic)        │  Vitest + jsdom or Node
                        │      (FR-U, 25 specs)         │  All src/lib/*.js
                        └───────────────────────────────┘
```

### 1.1 Cross-cutting infrastructure

```
┌──────────────────────────────────────────────────────────────────────┐
│  test/setup.js          vitest global setup: jsdom, localStorage    │
│  e2e/support.js         Playwright offline-mock boundary             │
│  scripts/security-check mjs                                          │
│  netlify/functions/lib/publicUrl.js  SSRF guard, already tested     │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 Why a pyramid, not a flat list

- **Time-to-failure** — the bottom layers (unit, contract) fail in seconds. A PR that breaks the build blocks in < 1 min.
- **Debuggability** — a unit test that fails points to a single function; a journey test that fails points to a system. The pyramid is a debugging ladder.
- **Maintenance** — small unit tests need no network; large journey tests need the offline-mock boundary to be intact. The pyramid lets us touch the bottom (most-frequent edits) without disturbing the top (rare edits).

```

datiq.globalSettings-> { guest_trial_soft_limit, guest_trial_reprompt_interval, ... }
scrapelite.*        -> legacy keys, copied by migrationService on first load
```

A new test helper (`test/fixtures/buildSubscription.js`, `test/fixtures/buildExtraction.js`) seeds any of these in one call. The helper uses `data-testid` rather than CSS class names where the page exposes them.

### 3.2 Test-data invariant

Every test that writes to localStorage in `beforeEach` MUST call the `resetLocalStorage()` helper, which removes the entire `datiq.*` and `scrapelite.*` namespaces. This guarantees the `R-5` risk ("test depends on real Supabase") cannot manifest as a false pass.

### 3.3 Migration impact

No production data shape changes. The five implementation fixes (FR-Z) are additive only.

## 5. State machines

### 5.0 Trial credit grant (Q2 — 2026-07-15)

```
fresh user lands on /
  → user is not logged in OR new signup
  → on signup success OR first successful extraction:
      credit = getEffectivePlanById(planId).trialCredit ?? 0
      if credit > 0 and not already granted:
        usage.usageCreditGranted = true  (persisted in datiq.usage or datiq.subscription)
        datiq.usage[monthKey()].extractions = max(0, current - credit)
        // OR: usage.bonusExtractions += credit
        // Decision: see ADR below.
  → credit grant is ONE-TIME per session/user
  → re-login does NOT re-grant (datiq.usage is preserved on logout per FR-S-01)
  → on plan upgrade mid-month, the credit is NOT re-applied
```

**Two implementation options, recorded in `sdlc/quality-gate/05-implementation-plan.md`:**

| Option | Pro | Con |
|---|---|---|
| **A. Subtract from current count** (e.g. `extractions = max(0, current - credit)`) | Simple to read; user sees "you have 25 free extractions" | Confusing when credit > current count |
| **B. Add to bonus pool** (`bonusExtractions += credit`) | Consistent with the existing "top-up bundle" pattern (Q2 says "fixed no of executions only as defined for different pricing options") | One more field to track |

**Chose B.** The Q2 answer ("fixed no of executions only as defined for different pricing options") maps cleanly to the `bonusExtractions` field that already powers Batch Pack bundles. Single code path, single test, single UI affordance.

**Where it lands:**
- `src/lib/usageService.js` → new `applyTrialCredit(planId)` function
- `src/components/AuthProvider.jsx` → call after `signUpWithEmail` resolves
- `src/components/BillingProvider.jsx` → fallback: call after first successful extraction if not yet applied
- Test: U-25 extension; new test: Z-02-EXT-01 (only Free plan grants; Select+ grants 0; one-time; survives logout)

**Data shape:**

```js
datiq.subscription = {
  planId: "free",
  activatedAt: "2026-07-15T10:00:00.000Z",
  addons: [],
  coupon: null,
  bonusExtractions: 25,    // ← new field; populated by applyTrialCredit
  trialCreditAppliedAt: "2026-07-15T10:00:00.000Z"  // ← guard for one-time
};
```

The existing `canExtract` and `canExtractBatch` already respect `bonusExtractions`, so no changes there. Pure additive change.

### 5.1 Payment flow (already exists; new tests verify each state)

```
IDLE
  → user clicks "Get Pro"
  → PREPARING (create-checkout)
  → PORTAL_OPEN (Razorpay modal)  ── cancel → CANCELLED
                                      └─ success → VERIFYING
  → ACTIVATING (plan write)
  → terminal: plan = "pro" (success) | CANCELLED | ERROR
  → ERROR has retryPayment() → PREPARING (same planId, same billingPeriod)
```

New tests assert each transition and the data side-effects (plan write, payment_events write, coupon_redemption write).

### 5.2 Guest trial gate

```
fresh mount
  → count=0, batchCount=0
  → user attempts extract #1..N
  → count++ per single extract, batchCount++ per batch
  → at count == soft_limit: SOFT_PROMPT (dismissible)
  → user dismisses: re-show after every N+1, N+3, ... (re-prompt interval)
  → at count == single_hard_limit: HARD_BLOCK (non-dismissible, overlay)
  → at batchCount == batch_hard_limit: HARD_BLOCK (reason: "batch")
  → sign-in: clear SOFT_PROMPT and HARD_BLOCK; preserve counts
  → sign-out: clear sensitive keys; preserve counts; navigate to /
  → reload while HARD_BLOCK: remount HARD_BLOCK
```

New tests assert every state in the machine, plus the "preserve on logout" invariant (AC-S-01).

### 5.3a Cross-browser support (Q7 — 2026-07-15)

```
playwright.config.js
  projects: [
    { name: "chromium", use: { browserName: "chromium" } },  // default; CI = this
    { name: "firefox",  use: { browserName: "firefox"  } },
    { name: "webkit",   use: { browserName: "webkit"   } },
  ]
  // Default CI behaviour: only chromium
  // `--project=firefox` and `--project=webkit` are opt-in

CI matrix:
  PR / push to main:  test:e2e:smoke --project=chromium  (~60s, fast feedback)
  Nightly workflow:   test:e2e:smoke:all-browsers  (manual trigger or cron)
  Developer local:    `npm run test:e2e:smoke:all-browsers` to validate before merging a risky change

Visual regression (FR-V-*): chromium-only on day 1. Cross-browser snapshots add flake; defer until the suite stabilises.

Trade-off recorded: chromium-only is faster and avoids multi-engine font-rendering flake; cross-browser catches engine-specific bugs (Safari date pickers, Firefox scrollbars). Net call: chromium for PR, all-browsers nightly, opt-in locally.
```

### 5.3 Auth flow (R3 onward)

```
fresh visit
  → check URL hash for #error=...: set authError, open modal, clean URL
  → user clicks "Sign in"  → AuthModal opens in sign-in tab
  → user clicks "Sign up"  → AuthModal opens in sign-up tab
  → user submits email
    → signInWithEmail  → on success: close modal, navigate to intended route
                         on error: keep modal open, show error
    → signUpWithEmail  → on success: close modal, navigate to intended route,
                         show "Check your email" toast
                         on error: keep modal open, show error
    → signInWithOAuth  → redirect to provider; on return, finish flow
  → user clicks "Sign out" → signOut → SENSITIVE_KEYS cleared, navigate to /
```

New tests cover all branches.

## 6. Failure modes

| Failure | User sees | Test that catches |
|---|---|---|
| `npm audit` reports a high/critical CVE | CI red; release blocked | security-check.mjs (existing) |
| `extract.js` returns 5xx and `useLocalStorage: true` | Save falls back to localStorage; toast "Saved locally" | FR-X-01, FR-C-03 |
| `verify-payment.js` HMAC fails | 400; user sees "Payment verification failed" | FR-X-05, FR-C-05 |
| `validateCoupon` returns `cap_reached` | Discount dropped, order created at full price | FR-C-04 |
| Razorpay modal closed by user | `status: "cancelled"`; plan unchanged | FR-S-07, FR-J-05 |
| `datiq.guestTrial` localStorage corrupted | Reset to default `{ count: 0, batchCount: 0, sid: null }` | FR-U-18 |
| `pricing_config` table missing | Server uses static tables | FR-C-18 |
| `validatePublicHttpUrl` rejects URL | 400 with reason | FR-C-01, FR-C-20 (existing) |
| Visual regression snapshot diff exceeds 0.2 % | Test fails; HTML report shows diff | FR-V-* |
| Axe reports a "serious" violation | Test fails; report shows node | FR-A-* |
| `useToast()` called as object | Component throws; message in console | FR-I-05 |

## 7. Trade-offs

| # | Option | Pro | Con | Why I chose / avoided |
|---|---|---|---|---|
| T-1 | **Per-route smoke spec** vs **one mega-smoke spec** | Per-route = focused failure; one file = simple to maintain | Per-route = ~23 files; one file = slow, hard to read | **Chose per-route** — Playwright parallelism makes 23 files faster, and a single failing page does not block 22 others |
| T-2 | **vitest-axe** vs **jest-axe** vs **@axe-core/playwright only** | vitest-axe fits the existing Vitest stack; jest-axe requires more setup; Playwright-only misses component-level a11y | vitest-axe is younger; some rules differ | **Chose vitest-axe + @axe-core/playwright** — both, for component + page coverage |
| T-3 | **Mock at the network layer** (`page.route("**/api/**")`) vs **mock at the import layer** (`vi.mock("../../../src/lib/apiClient.js")`) | Network mocking is the current pattern; import mocking is faster but locks to module identity | Network mocking = slower; import mocking = maintenance burden on refactor | **Chose network for Playwright; import for Vitest contract** — both have a clear home |
| T-4 | **One `AppProviders` test harness** vs **per-test provider tree** | One harness = DRY; per-test = focused | One harness = re-uses a fragile mount; per-test = verbose | **Chose one harness** (`src/__tests__/harness/AppProviders.jsx`) — already a pattern in similar codebases |
| T-5 | **Coverage threshold at 80 % day-1** vs **70 % with a roadmap to 80 %** | 80 % forces coverage; 70 % is achievable | 80 % may fail on day 1; 70 % is easy to forget | **Chose 70 % on day 1, 80 % in R+1** — see Risk R-2 |
| T-6 | **Adopt Playwright `toHaveScreenshot`** vs **Percy / Chromatic / Loki** | Playwright is the existing tool; paid tools add infra | Playwright snapshots are noisier; paid tools have a UI for review | **Chose Playwright** — free, deterministic, works with our existing CI |
| T-7 | **Split `test:e2e` into smoke / journeys / a11y / visual** vs **one big suite** | Split = faster PRs (smoke only), better debugging | Split = 4 commands to wire in CI | **Chose split** — see FR-I-CI-04 |
| T-8 | **ESLint config (I-1) in this initiative** vs **separate PR** | One PR is simpler; separate PR is reviewable | One PR mixes intent; separate PR delays value | **Recommend separate PR** (Q1) — keep this PR focused on tests |
| T-9 | **Real Stripe / Razorpay integration tests** vs **mocks only** | Real = catches provider regressions; mocks = safe, fast | Real = flakiness, cost, credentials in CI | **Chose mocks only** — see Risk R-5 and Out-of-scope |
| T-10 | **Cross-browser (Firefox/Webkit)** vs **chromium-only** | Cross-browser = broader coverage; chromium-only = faster | Cross-browser = 2-3× CI time | **Chose chromium-only** — Q7 defer |

## 8. Rejected alternatives

- **Adopt Cypress.** Rejected — Playwright is already in the project, has better cross-browser story, has `toHaveScreenshot`, and has `@axe-core/playwright`.
- **Adopt Testing Library + jsdom-only end-to-end (no browser).** Rejected — the app uses `localStorage`, `sessionStorage`, `IntersectionObserver`, `ResizeObserver`, and `URL.createObjectURL`, all of which need real browser semantics. Playwright is the right tool.
- **Adopt MSW for the API mocking layer.** Rejected — `e2e/support.js` already intercepts at the network layer; MSW would be a second layer of mocking. We move to MSW only if a future test needs a real fetch in jsdom (D.2 II-8).
- **Per-R-number test files (e.g. `R19-scheduler.test.js`).** Rejected — tests should be organised by surface, not by release. R-numbered features land in their own `*.test.js` next to the file they exercise.
- **A central "test DB" (real Supabase, seeded per test).** Rejected — see R-5 and T-9. The offline-mock boundary is the project's hard rule.
- **A custom JSDOM polyfill for `crypto.randomUUID`.** Rejected — `crypto.randomUUID` is available in Node 19+ and jsdom 22+; we are on jsdom 25.

## 10. Test naming and conventions

- `describe("ComponentName", () => { it("does X when Y", ...) })` — already used in Vitest.
- Playwright `test("description in plain English", async ({ page }) => { ... })` — already used.
- **No `it.only` / `test.only`** in committed code — CI will fail the build (`forbidOnly: true`, already set).
- **No `await page.waitForTimeout(500)`** — use `expect(locator).toBeVisible()` with a timeout instead.
- **No `Date.now()` in test bodies** — use `vi.useFakeTimers()` and `vi.setSystemTime(...)`.
- **No real fetch** — use `page.route()` (Playwright) or `vi.mock("node:fetch")` (Vitest contract).
- **No `crypto.randomUUID()` without a deterministic override** — most tests pass an explicit `id`.

## 11. Coverage strategy

The Vitest config currently scopes coverage to 6 hand-picked `src/lib/*.js` files at 70 %. After this initiative:

| Scope | Threshold | Justification |
|---|---|---|
| `src/lib/utils.js` | 80 % | Most-tested today; user-visible exports |
| `src/lib/pricingMath.js` | 90 % | Money math — must be near-100 % |
| `src/lib/usageService.js` | 90 % | Plan-limit math — same |
| `src/lib/currencyService.js` | 80 % | Locale coverage; tested with multiple Intl inputs |
| All other `src/lib/*.js` | 80 % | Default new threshold |
| `src/components/*.jsx` (covered) | 60 % | Component tests focus on observable behaviour; styles not counted |
| `src/pages/*.jsx` (covered) | 50 % | Most coverage comes from functional + integration tests, not unit |

The threshold is enforced in `vite.config.js` (FR-I-CI-03). A daily cron can re-enforce stricter thresholds as the suite grows.
